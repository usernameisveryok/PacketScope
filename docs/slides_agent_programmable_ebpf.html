Network defense has relied on rules for decades: IP blocklists, 5-tuple firewall policies, signature-based IDS. These rules work for known threats but can't adapt to novel attacks, track state across packets, or reason about traffic patterns over time.

The standard response has been to add ML models — train a small neural network on labeled traffic, deploy it as an inference engine. But small models have limited capacity, require retraining for new threat classes, and suffer from catastrophic forgetting when the distribution shifts.

What if we don't put all our attention on model weights? What if, instead, a coding agent writes and continuously maintains actual eBPF defense code that runs at the kernel's XDP data plane?

That made us rethink the eBPF filter: hand-written kernel filtering logic. It was never useless; it was simply too expensive to maintain. Coding agents change that maintenance curve. An eBPF filter that used to be a one-off patch can become code worth owning for the long term — a defense system that keeps growing.

网络防御依赖规则已有数十年：IP 黑名单、五元组防火墙策略、基于签名的 IDS。这些规则对已知威胁有效，但无法适应新型攻击、跨数据包追踪状态，或随时间推理流量模式。

标准的应对方案是引入 ML 模型——在标注流量上训练一个小型神经网络，部署为推理引擎。但小模型容量有限，遇到新威胁类别需要重新训练，且在分布漂移时会灾难性遗忘。

如果我们不把所有注意力放在模型权重上呢？如果让一个 coding agent 持续编写和维护运行在内核 XDP 数据面上的 eBPF 防御代码呢？

这让我们重新审视 eBPF 过滤器：手写的内核过滤逻辑。它从不是没用的；只是维护成本太高。Coding agent 改变了这条维护曲线。一个原本只是一次性补丁的 eBPF 过滤器，可以成为值得长期持有的代码——一个不断成长的防御系统。

# The Anomaly 异象

While extending PacketScope's Guarder module, we wanted to move beyond static 5-tuple rules. The original system had a fixed array of 32 filter_rule structs, matched sequentially in the XDP hook. An AI could generate rule JSON, but the underlying logic was always the same linear scan.

The initial question was:

Can a coding agent write eBPF C code that implements defense logic too complex for any fixed rule template, and keep improving it over iterations?

We gave the agent a natural language intent — "detect and mitigate SYN flood attacks with per-IP rate limiting" — and let it generate eBPF C code. After a few iterations with traffic feedback:

  • The first version was a simple port-based drop rule (equivalent to a static rule).
  • After seeing traffic logs, the agent added per-IP counters using hash buckets.
  • After seeing false positives, it added time-window decay so counters reset every second.
  • After seeing evasion attempts, it added TCP flag validation and SYN-ACK tracking.
  • The final version was a 45-line eBPF program with stateful, adaptive, per-IP SYN flood detection — something no combination of static rules could express.

The raw capability was interesting. But the more significant observation was: the code kept growing in sophistication. Each iteration didn't discard previous logic; it extended it. The agent was maintaining a software system, not training a model.

在扩展 PacketScope 的 Guarder 模块时，我们想超越静态五元组规则。原系统有一个固定的 32 条 filter_rule 结构体数组，在 XDP hook 中顺序匹配。AI 可以生成规则 JSON，但底层逻辑始终是相同的线性扫描。

最初的问题是：

一个 coding agent 能否编写 eBPF C 代码，实现任何固定规则模板都无法表达的复杂防御逻辑，并持续迭代改进？

我们给 agent 一个自然语言意图——"检测并缓解 SYN 洪水攻击，实现每 IP 速率限制"——让它生成 eBPF C 代码。经过几轮流量反馈迭代后：

  • 第一个版本是简单的基于端口的丢弃规则（等价于静态规则）。
  • 看到流量日志后，agent 添加了基于哈希桶的每 IP 计数器。
  • 看到误报后，它添加了时间窗口衰减，计数器每秒重置。
  • 看到绕过尝试后，它添加了 TCP 标志验证和 SYN-ACK 追踪。
  • 最终版本是一个 45 行的 eBPF 程序，具有有状态的、自适应的、每 IP SYN 洪水检测——这是任何静态规则组合都无法表达的。

原始能力本身就很有趣。但更重要的观察是：代码在不断增长复杂度。每次迭代不会丢弃之前的逻辑；而是扩展它。Agent 维护的是一个软件系统，而不是训练一个模型。

# Defense Learning 防御学习

Inspired by Heuristic Learning, we define Defense Learning (DL) as the process where a coding agent continuously maintains and improves a defense system — not by updating neural network weights, but by editing verified kernel code.

The key properties:

  • DL is built out of program code — eBPF C source, compiled to kernel-verified bytecode.
  • Like Deep RL, it has a loop of state (traffic), action (filter verdict), and feedback (drop counts, false positive reports, new attack patterns). Unlike Deep RL, the object being updated is software structure, not parameters.
  • Its feedback is consumed by a coding agent, and can come from: kernel drop/pass counters, connection logs, PCAP replays, operator reports, or threat intelligence feeds.
  • Its updates do not use backpropagation. The agent directly edits filter logic, state tracking, detection thresholds, or adds entirely new defense modules.
  • The maintained object is a Defense System (DS) — more than an isolated filter. It contains programmatic filters, state representations, feedback channels, audit logs, and an update mechanism driven by the coding agent.

受 Heuristic Learning 启发，我们定义防御学习 (Defense Learning, DL)为 coding agent 持续维护和改进防御系统的过程——不是通过更新神经网络权重，而是通过编辑经过验证的内核代码。

关键属性：

  • DL 由程序代码构建——eBPF C 源码，编译为内核验证的字节码。
  • 与 Deep RL 类似，它有状态（流量）、动作（过滤判定）和反馈（丢弃计数、误报报告、新攻击模式）的循环。与 Deep RL 不同，被更新的对象是软件结构，而非参数。
  • 反馈由 coding agent 消费，可来自：内核丢弃/通过计数器、连接日志、PCAP 回放、运维报告或威胁情报源。
  • 更新不使用反向传播。Agent 直接编辑过滤逻辑、状态追踪、检测阈值，或添加全新的防御模块。
  • 维护的对象是一个防御系统 (Defense System, DS)——不仅仅是一个独立的过滤器。它包含编程式过滤器、状态表示、反馈通道、审计日志和由 coding agent 驱动的更新机制。

# Why This Didn't Work Before 为什么以前不行

The idea of "code as defense logic" is not new. Snort rules, iptables chains, and BPF classic filters are all forms of it. What's new is the economics of maintenance.

Hand-written eBPF filters required:

  • A kernel engineer who understands BPF verifier constraints
  • Manual iteration: write C, compile, load, test, read logs, repeat
  • Careful state management across kernel updates
  • One-off patches that nobody maintained after deployment

The result: complex eBPF defense logic was too expensive to write and too fragile to maintain. Organizations defaulted to static rules or bought proprietary appliances.

Coding agents change this equation. An LLM agent can:

  • Generate eBPF C code from natural language intent in seconds
  • Read kernel verifier error messages and fix its own code
  • Consume traffic telemetry and iterate on filter logic
  • Maintain and extend a growing codebase across deployments

The maintenance cost that killed hand-written eBPF filters is now borne by the agent. What used to take a kernel engineer a week now takes an API call and a compilation step.

"代码作为防御逻辑"的想法并不新鲜。Snort 规则、iptables 链和 BPF classic 过滤器都是其形式。新的是维护的经济性。

手写 eBPF 过滤器需要：

  • 一个理解 BPF 验证器约束的内核工程师
  • 手动迭代：写 C、编译、加载、测试、读日志、重复
  • 跨内核更新的谨慎状态管理
  • 部署后无人维护的一次性补丁

结果：复杂的 eBPF 防御逻辑写起来太贵，维护起来太脆弱。组织默认使用静态规则或购买专有设备。

Coding agent 改变了这个等式。一个 LLM agent 可以：

  • 在几秒内从自然语言意图生成 eBPF C 代码
  • 读取内核验证器错误消息并修复自己的代码
  • 消费流量遥测并迭代过滤逻辑
  • 跨部署维护和扩展一个不断增长的代码库

过去杀死手写 eBPF 过滤器的维护成本，现在由 agent 承担。过去需要内核工程师一周的工作，现在只需一次 API 调用和一次编译。

# How It Does Continual Defense 如何持续防御

The core advantage over both static rules and ML models: the defense system accumulates knowledge as verified code, and never forgets.

A neural network for packet classification stores knowledge as weights. When you retrain for a new threat class, old knowledge can degrade (catastrophic forgetting). When you fine-tune, the model drifts. When the threat landscape shifts, you need new training data.

An agent-maintained eBPF filter stores knowledge as code:

  • New threats add new code paths — they don't overwrite existing ones
  • Each defense module is composable — SYN flood detection in slot 0, DNS tunneling in slot 1, port scan detection in slot 2, chained via tail calls
  • Old logic persists — adding a new filter doesn't change what previous filters do
  • Knowledge is auditable — you can read exactly what the defense does in C source
  • Updates are atomic — tail call slot swap is instant, zero-downtime

相比静态规则和 ML 模型的核心优势：防御系统将知识积累为经过验证的代码，永远不会遗忘。

用于数据包分类的神经网络将知识存储为权重。当你为新威胁类别重训练时，旧知识可能退化（灾难性遗忘）。微调时模型会漂移。当威胁格局变化时，你需要新的训练数据。

Agent 维护的 eBPF 过滤器将知识存储为代码：

  • 新威胁添加新代码路径——不会覆盖现有路径
  • 每个防御模块可组合——SYN 洪水检测在 slot 0、DNS 隧道在 slot 1、端口扫描检测在 slot 2，通过尾调用链接
  • 旧逻辑持久存在——添加新过滤器不会改变之前过滤器的行为
  • 知识可审计——你可以在 C 源码中精确阅读防御逻辑
  • 更新是原子的——尾调用 slot 交换瞬间完成，零停机
Key insight: 关键洞察： Continual Learning in neural networks is hard because of weight interference. Continual Learning in code is natural — you just keep adding functions. The agent turns network defense into a software engineering problem, where "continual learning" is just "software maintenance." 神经网络中的持续学习之所以困难，是因为权重干扰。代码中的持续学习是自然的——你只需不断添加函数。Agent 将网络防御变成了软件工程问题，"持续学习"只是"软件维护"。

# The Safety Model 安全模型

Letting an AI write kernel code sounds dangerous. It is — unless you have an unforgeable safety oracle. We do: the Linux eBPF verifier.

Every eBPF program, regardless of how it was generated, must pass the kernel verifier before it can execute. The verifier mathematically proves:

  • All memory accesses are within bounds
  • The program terminates (no infinite loops)
  • No kernel pointer leaks to user space
  • All map accesses use correct types and keys
  • Stack usage is bounded

On top of this, we add three more layers of defense-in-depth:

让 AI 写内核代码听起来很危险。确实如此——除非你有一个不可伪造的安全预言机。我们有：Linux eBPF 验证器。

每个 eBPF 程序，无论如何生成，都必须在执行前通过内核验证器。验证器数学证明：

  • 所有内存访问都在边界内
  • 程序终止（无无限循环）
  • 无内核指针泄漏到用户空间
  • 所有 map 访问使用正确的类型和键
  • 栈使用有界

在此基础上，我们添加了三层纵深防御：

Layer 层级 Mechanism 机制 What It Catches 捕获内容
1. Static Sandbox Regex + keyword blocklist 正则 + 关键词黑名单 Banned helpers (bpf_probe_read, bpf_redirect), #include, asm, map declarations, while loops 禁用辅助函数、#include、asm、map 声明、while 循环
2. Template Confinement Agent code injected into safe wrapper Agent 代码注入安全包装器 Cannot declare functions, structs, maps, or SEC annotations 无法声明函数、结构体、map 或 SEC 注解
3. Compiler clang -Wall -Werror -target bpf Type errors, undefined behavior, invalid constructs 类型错误、未定义行为、无效构造
4. Kernel Verifier Mathematical proof by Linux kernel Linux 内核数学证明 Memory safety, termination, resource bounds — unforgeable 内存安全、终止性、资源边界——不可伪造
Even if the LLM is adversarially prompted, the kernel verifier is the final gatekeeper. 即使 LLM 被对抗性提示，内核验证器也是最终的守门人。 No AI-generated code runs in the kernel without passing a formal verification step that the AI cannot bypass. 没有 AI 生成的代码能在未通过 AI 无法绕过的形式化验证步骤的情况下在内核中运行。

# The Next Paradigm? 下一个范式？

The pattern we're seeing — a coding agent continuously maintaining and growing a verified software system — may extend well beyond network defense.

Consider: anywhere you currently deploy a small ML model because "it's good enough and we don't have time to write complex logic," you could instead deploy agent-maintained code. The code starts simple, but unlike the model, it keeps growing. It never forgets. It's interpretable. It's formally verified where the runtime supports it.

Network defense is a particularly good fit because:

  • eBPF provides a formal safety oracle (the verifier) that makes AI-generated code safe by construction
  • Feedback is cheap and continuous (every packet is a data point)
  • The execution environment (XDP) is deterministic and reproducible
  • Defense requirements change faster than any model can be retrained

We believe this represents a shift in how AI intersects with systems programming: not AI replacing code, but AI writing and maintaining code that grows more capable over time. The system is not a model. It's a living codebase.

我们看到的模式——coding agent 持续维护和增长一个经过验证的软件系统——可能远不止于网络防御。

考虑：任何你目前部署小型 ML 模型的地方，因为"够用了，我们没时间写复杂逻辑"，你都可以改为部署 agent 维护的代码。代码从简单开始，但与模型不同，它持续增长。它永不遗忘。它可解释。在运行时支持的地方，它是形式化验证的。

网络防御是特别好的应用场景，因为：

  • eBPF 提供了形式化安全预言机（验证器），使 AI 生成的代码在构造上就是安全的
  • 反馈廉价且连续（每个数据包都是一个数据点）
  • 执行环境（XDP）是确定性和可复现的
  • 防御需求的变化比任何模型的重训练都快

我们认为这代表了 AI 与系统编程交叉方式的转变：不是 AI 替代代码，而是 AI 编写和维护随时间变得更强大的代码。这个系统不是一个模型。它是一个活的代码库。
